## 1. 命名规范

### 1.1 通用宗旨

| # | 规则 | 反例 / 说明 |
|---|---|---|
| 1 | 望文生义、简约明了，力求免沟通 | — |
| 2 | 用常用、简单的英文单词，拼写要正确 | — |
| 3 | 工程名小写，不用驼峰 | — |
| 4 | Java 常量全大写；前端变量与普通变量无异 | `MAX_COUNT` |
| 5 | 变量、方法名小写开头，词界用驼峰 | `orderCount` |
| 6 | 长尾命名；**严禁**用 `date`、`string` 这类与对象名重复的词 | — |
| 7 | 不要用 `a`、`b` 这种名字——要考虑方便全局搜索 | — |
| 8 | 也别又臭又长，可适当省略元音保持简洁 | — |
| 9 | 不要有肉眼难分辨的形近名 | ❌ `allocationWorkingHours` vs `availableWorkingHours` |
| 10 | 尽量不用汉语拼音 | — |
| 11 | 单词要符合业务"暗示"，用复数代表多个；用后缀表类型：`arr` 表数组、`list` 表集合 | `orders` |

### 1.2 变量命名：属性名前置

```js
let orderCount;      // 订单数量
let ordersCount;
Integer orderCnt;
int ordersCnt;
```

### 1.3 方法命名：动词开头，属性名后置

| 示例 | 写法 |
|---|---|
| 创建订单 | `createOrder()` |
| 查询订单 | `queryOrders()` |

**查询方法前缀约定（必须遵守）：**

| 前缀 | 含义 | 示例 |
|---|---|---|
| `list` | 取回一个**集合** | `listOrdersByName()` |
| `get` | 取回**一个对象** | `getOrderByType()` |
| `find` / `select` / `query` | 动态查询条件，配合 `One` / `All` / `Some` | `findOne()`、`selectSome()` |
| `page` | 分页查询 | `pageOrders()` |

**方法名中介词的约定：**

| 介词 | 含义 | 示例 |
|---|---|---|
| `by` | 以什么 | `findByID(String id)` |
| `at` | 当什么 | `findAtDate(Date day)` |
| `in` | 包含什么 | — |
| `with` | 有什么 | — |
| `without` | 排除没带什么 | — |

### 1.4 各端命名必须统一

前端、后端、移动端、数据库、服务器、redis、docker 等的命名**高度保持一致**。

### 1.5 后端命名规范（MVC）

**Controller 层**

| 规则 | 说明 |
|---|---|
| 类名 | 以 `XxxController` 为后缀 |
| 映射路径 | `@RequestMapping("/模块/类名全小写")`，如 `/sku/goodsstore` 或 `/sku/goods_store`；**不要驼峰** `@RequestMapping("/sku/goodsStore")` |
| 注入 | 有接口时**用接口注入**：`@Autowired private IGoodStoreService goodStoreService;` |
| ⛔ 跨层 | **Controller 不能直接调用 Mapper 层**（规范截图反例：Controller 里注入 `TestplanMapper` 被红叉标错） |

**Service 层**

| 规则 | 说明 |
|---|---|
| 接口 | `IXxxService` |
| 实现 | `XxxService`（均以 Service 为后缀） |
| 职责 | 控制事务 |

**Manager 层**：控制缓存。

**Mapper / Dao 层**

| 规则 | 说明 |
|---|---|
| Entity 命名 | **去掉数据库表前缀**：`t_user` 对应 `User`，不是 `TUser` |
| MyBatis | 以 `Dao` / `Mapper` 为后缀 |
| SQL 位置 | **三行以内的 SQL 尽量直接写在 Mapper 接口中** |

**JavaBean 命名规范**

| 规则 | 说明 |
|---|---|
| 基本类型 | 必须使用包装类型（`Integer`、`Double`、`Boolean` 等） |
| 逻辑 | 不得有任何业务逻辑或计算 |
| 默认值 | 不允许有任何默认值 |
| 位置 | 实体放 `entity` 包，是数据库持久对象 |

**数据对象后缀（VO / DTO / FORM / BO）**

| 后缀 | 方向 | 使用范围 |
|---|---|---|
| `VO` | 后端 → 前端 / rpc 的业务数据封装 | 只能用于返回前端、rpc。例：`studentVO` |
| `DTO` \| `FORM` | 前端 → 后端 | 接收提交数据 |
| `BO` | 内部逻辑处理对象 | 只能用于 service、manager、dao 层，**不得用于 controller 层** |

### 1.6 前端命名规范

**目录、文件、组件命名**

全部小写、中划线分隔，**不用驼峰**（因为不用大写）：

```text
✅ 正例：category-tree-select
❌ 反例：category_tree-select、categoryTree-select
```

**引号与分号**

| 位置 | 规则 |
|---|---|
| HTML、Vue template 的标签属性 | 用**双引号** |
| 所有 JS 中的字符串 | 用**单引号** |
| 所有 JS 代码行 | 换行要加**分号** |

**Vue3 组合式 API**

| 规则 | 说明 |
|---|---|
| 组件 | **必须使用 `setup` 语法糖**，全局统一 |
| 代码组织 | 必须用模块化思想拆分，把相互关联的代码放在一起 |

```vue
<script setup>
// 各种需要导入
import xxxxx;
import { productApi } from '@/api/goods/product.js';
import goodsAPI from '@/api/goods/goods.js';
// -------- 1. 解构导入的方法，用 'Api' 后缀与本地方法区分（需在 product.js 中定义方法时同步修改） --------
// -------- 2. 导入一个完整的对接后端的 js 文件时，用 'API' 后缀进行强调 --------
</script>
```

### 1.7 前端 API 导入与命名的后缀规则（重点，截图专门强调）

| 场景 | 后缀 | 示例 |
|---|---|---|
| **解构导入**接口文件里的方法 | `Api`（首字母大写） | `import { doFinishApi, sendMsgApi } from '@/api/sprint/sprint_bklg/springblg.js';` |
| **整个文件导入**对接后端的 js | `API`（全大写） | `import productAPI from '@/api/product/product/product.js';` |
| 本页面同名、唯一的接口文件 | 可省略为 `api` | `import api from '@/api/attachment/attachment.js';` |

⚠️ 接口文件里定义的每个方法**都必须带 `Api` 后缀**——截图反例：`getOne`（✗）、`listUsers`（✗）；
正确写法 `doFinishApi`（✓）、`listApi`（✓）、`sendMsgApi`（✓）、`listBySBLId`（✓）。

### 1.8 模板引用变量 Ref

| 规则 | 说明 |
|---|---|
| 声明 | 用 `ref()` 方法、**参数为空**声明 |
| 变量名 | 必须以 `Ref` 结尾 |
| template 里的 `ref` 属性值 | 也必须以 `Ref` 结尾 |

```vue
<input ref="inputRef">

<script setup>
const inputRef = ref();
</script>
```

**注释要求**：使用 Composition API 编写时，**变量必须加注释、方法必须加注释**。

```js
// 查询 公告 默认值
const queryFormState = {
  noticeTypeId: undefined,  // 分类
  keywords: '',             // 标题、作者、来源
  documentNumber: '',       // 文号
  publishTimeEnd: null,     // 发布-截止时间
  pageNum: 1,
  pageSize: PAGE_SIZE,
};

// 查询 公告 请求表单
const queryForm = reactive({ ...queryFormState });
```

## 2. 后端分层规范

| 规则 | 说明 |
|---|---|
| Controller 归属 | PC 端后端与移动端**独立、不混用** |
| 共用规则 | Controller 共用 Dao / Service / Manager 层时，**以 PC 端为准**；即移动端 Controller 调用 PC 端 Service 层 |
| 映射唯一性 | **避免一张表多个映射，保证映射的全局唯一性** |

## 3. 注释和代码一样重要

注释除了说明作用、逻辑之外，当业务逻辑过于复杂、代码过于庞大时，注释就是让逻辑思路变清晰的路标。

**后端类头注释模板**（规范截图标准样式）：

```java
 * @ClassName: SprintBacklogController
 * @Description: SprintBacklog-控制器
 * @author: LJC

 */
```

## 4. Git 提交规范

| # | 规则 |
|---|---|
| 4.1 | 提交前**先 pull 一次**。提交前发生冲突比提交后发生冲突容易解决得多 |
| 4.2 | **切忌全部提交**，只提交自己本次更新的文件 |
| 4.3 | 用**分支/合并**开发：分支名 = 自己的昵称 + 日期，如 `rick0427`；合并后按通知 pull 代码，合并回旧分支或开新分支继续开发 |
| 4.4 | 提交前仔细检查，确保**新增文件已勾选加入版本控制** |
| 4.5 | 提交前**先编译一次**保证能正确运行，防止出现编译都报错的情况 |
| 4.6 | 提交注释要准确简洁地表达本次提交内容，如「新增 XX 功能」 |
| 4.7 | 对应 scrum 系统任务或 bug 时，格式：`task#[任务id] [任务标题] [具体事项]` / `bug#[bug id] [bug标题] [具体事项]` |
| 4.8 | **必须添加 `.gitignore`**：不提交 idea 配置、`target/`、前端 `dist/`、`node_modules/` 等无关内容 |

## 5. 数据库规范

| # | 规则 | 说明 |
|---|---|---|
| 5.1 | **货币以整数计，单位为分** | 与第三方支付平台保持一致 |
| 5.2.1 | **字段引用类型必须与被引用类型一致**，避免丢精度 | 截图反例：主表 `id varchar(32)`，子表关联字段却写成 `int`（`clzid int(11)` 被红字标「类型不相同」）；另一张表 `orderid decimal` 与关联的 `varchar` 不一致也被标错 |
| 5.2.2 | **库名统一小写**，禁止驼峰、中文、特殊字符 | 业务模块命名：`userdb`、`orderdb`、`goodsdb` |
| 5.2.3 | **表名统一小写 + 下划线**，禁止驼峰、中文、特殊字符；长度 ≤ 30 字符；避免数据库关键字 | 中间关联表：`表1_表2`，如 `user_order`、`t_user_order` |

## 6. RESTful 接口规范

| # | 规则 |
|---|---|
| 6.1 | 后端接口 **uri 全部小写**，命名 `模块-类-功能`，与 package / class / 方法别名保持一致，有较高辨识度 |
| 6.2 | 获取数据尽量用 **get**，提交数据用 **post** |
| 6.3 | 后端接口一定要有详细注释；swagger 接口注释**必须加上后端作者、更新时间** |
| 6.4 | 前端 api 接口**以页面为单位**，功能分类命名与后端保持高度一致 |

### 6.5 URL 三段映射实例（截图规则，前端照此对齐后端）

后端代码与 URL 的对应关系（类头 `@RequestMapping("/模块/类名全小写")` + 方法级映射）：

| Java 元素 | 示例 | 映射到 URL |
|---|---|---|
| 包名（模块） | `com.ossjk.qlh.tst.controller` | `/tst` |
| `@RequestMapping`（类名） | `TestplanController` → `@RequestMapping("/tst/testplan")` | `/tst/testplan` |
| 方法（驼峰转小写下划线） | `@GetMapping("/ls")` | 完整 URL：`http://127.0.0.1:8146/scrum/tst/testplan/ls` |

前端 api 文件的方法名与 URL 的映射（`devRecord.js` 截图规则）：

| 前端方法 | 后端 URL | 要点 |
|---|---|---|
| `listApi` | `/sprint/devrecord/list` | 包名 + 类名全小写 + 方法名 |
| `listUsers` | `/sprint/devrecord/list_users` | 驼峰 `U` **必须转下划线**（写 `list_Users` 是错的） |
| `listBySBLId` | `/sprint/devrecord/list_by_sblid` | 多词驼峰全部转小写下划线 |

> 口诀：**「后端的包名 + 类名 + 方法名，驼峰大写一律转下划线，整条 URL 全小写」**。
